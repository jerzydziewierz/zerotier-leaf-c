# Checks and proofs attempted

State: 2026-11-13, after two independent reviews. This report lists every check and proof that was tried on the C leaf, in plain words: what was asked, which tool answered, the result, and what the result does not show. No prover runs on the workstation. Run them on another host with `proofs/on-remote.sh start` then `proofs/on-remote.sh wait` (a few minutes), and `proofs/on-remote.sh start mutate` for the deliberate errors; exit status 0 of `wait` means every tool ran and reported the expected result. The large CBMC harnesses run one per unit with `proofs/remote.sh`.

## What is under test

Three modules so far, the receive front end: the classifier `ztl_classify()` (`src/wire.c`), the reassembly `ztl_reasm_input()` (`src/reasm.c`) and the receive gate `ztl_rx()` (`src/rx.c`). Together 1,034 bytes of code on the Cortex-M7 at `-Os`. The cryptography behind the gate does not exist yet. The sections below take them one at a time.

The classifier (186 bytes of code, 24 bytes of stack) receives the payload of one UDP datagram from the network, a pointer and a length, and decides one of three things:

- **Head**: the datagram is a candidate ZeroTier packet, or the first part of one. Rule: length 28 to 2048 bytes; byte 13 is not `0xff`; in the flags (byte 18) the cipher suite (bits 3 to 5) is 1, or it is 0 and bit 7 is clear. (Suite 0 with bit 7 is "extended armor", which needs AES. Suite 1 with bit 7 is normal: peers up to version 1.14 set that bit on every encrypted packet.)
- **Fragment**: the datagram is the second part of a packet that was cut in two. Rule: length 17 to 2048 bytes; byte 13 is `0xff`; byte 14 is `0x21` ("part 1 of 2").
- **Drop**: everything else.

For a head or a fragment it fills a small record (`struct ztl_view`) with the packet number and with pointers to the addresses and the payload inside the caller's buffer. For a drop it must not touch that record. "Candidate" is meant literally: nothing in the datagram is trusted or authenticated at this point.

## Three kinds of tool

| Tool | How it works, in one sentence | Strength | Weakness |
|---|---|---|---|
| **CBMC** (bounded model checker) | It turns the program and "any input up to this size" into one large logic formula and asks a solver for an input that breaks a check. | Exact within the bound; handles bit operations with ease; gives a counterexample. | Says nothing beyond the bound. |
| **Frama-C Eva** (abstract interpretation) | It runs the program on sets of values instead of single values. | Never misses a run-time error on the paths it analyses; no annotations needed. | Can raise false alarms; cannot decide properties that depend on unknown input bytes. |
| **Frama-C WP** (deductive proof) | It turns the code and a written contract into logic formulas ("goals") and gives each to automatic provers. | No bound and no approximation: holds for every input. | Needs a written contract; provers are weak on bit operations. |

A "contract" states what must be true before the call (the buffer is readable for `len` bytes, the record is writable, the two do not overlap) and what is true after it (the three rules above and the exact value of each field). It is in `include/ztl/wire.h`.

## Attempts on reassembly

`ztl_reasm_input()` in `src/reasm.c` (494 bytes of code, at most 88 bytes of stack, 4,144 bytes of RAM for two waiting packets, no call into a C library) joins a packet that arrives as a head and one fragment. Rules: either order of arrival gives head bytes followed by the fragment payload; a total above 2048 bytes gives nothing; a second head or second fragment for a waiting packet is ignored; parts more than 5 s apart are not joined; with no free place the oldest waiting packet is replaced. The result is not yet authenticated.

The module is built from small functions, each with its own contract (`src/reasm_internal.h`): copy bytes; move bytes down inside one buffer; choose a slot; put a head into a slot; put a fragment into a slot. **Each function is proved against its contract alone, and a caller is proved with the contracts of what it calls, not with their code.** That is why these proofs hold at the full 2048-byte size and take seconds: the provers never follow a copy byte by byte, they use "after the call, byte j of the destination equals the old byte j of the source".

## Attempts on the receive gate

`ztl_rx()` in `src/rx.c` (96 bytes of stack) is the only way a packet reaches the rest of the node. Order of steps: classify; the datagram must be addressed to this node and must not claim to come from it; reassemble; on the complete packet apply the address rule again, find the source in the table of pinned peers, refuse an unencrypted packet unless it is HELLO, then call the authentication primitive with that peer's key. Only a "yes" from the primitive delivers the packet. The primitive itself (Salsa20/12 and Poly1305) is not written yet; the gate is checked with a stand-in that may answer yes or no for any input, so the result does not depend on the cryptography.

## What all of this does not show

- Only the receive front end exists: classifier, reassembly, gate. The gate is proved against a primitive that is only a contract. The cryptography, key handling, the protocol messages, sending, and the Zephyr adapter do not exist yet.
- **The rules are a reading of the reference source.** A proof shows that the code follows the written rules, not that the rules are right. F-7, F-8 and F-10 were errors of this kind, and no tool found them. A-2 now compares against a model of the reference receive path (V-13); the model is still written by hand, and older peer versions matter as well as the pinned reference.
- "Accepted" does not mean "authentic". A head or fragment is still untrusted data.
- The record holds pointers into the caller's buffer, and it does not keep the raw flags. Nothing yet proves that later code stops using the pointers before the buffer is reused, or that it reads the flags again correctly.
- The proofs use the tools' models of C (64-bit and 32-bit). The target's exact struct layout, the compiler and timing are outside them (V-17).
- New source files are not picked up by the runner on their own: it lists its units by name. A file that reads network input without a proof would not make the run fail (V-21).
- The contracts are written by hand. A contract that is too weak proves less than it seems to; the deliberate errors (A-6, B-6) and the CBMC cross-checks (B-3, B-4) are the guard against that.

## Independent reviews

Two other models, here called model A and model B, reviewed the proofs, read-only (model B on the improved state). Their claims were checked against the files before any change.

**Review 1 (model A)** found F-3 and F-6 and that the first Eva summary did not support the claim "postconditions checked". Its main advice: prove behaviour across packets before adding more provers to one small function. Its proposals are V-1 to V-12 in `CHECKLIST.md`: authentication before effects; nonce life cycle; replay; reassembly; bounded cost and recovery under hostile input; timer and counter wrap; Zephyr buffer ownership; secret lifetime; constant time; cryptographic correctness; trace equivalence with the reference; whole-system RAM, stack and compiled-code bounds.

**Review 2 (model B)** found F-7, F-8, the second half of F-6 and F-9, the unclear check counts, the over-broad "0 alarms" wording for Eva, and the wrong statement that alignment is no risk for this function. It also showed that R-1 says nothing about peers with encrypted HELLO. Its main point: the correctness of the rules is now the weakest link. Its proposals are V-13 to V-23: classification equal to a model taken from the reference receive path; exact consumption of variable-length records; version and cipher negotiation as a state machine; reply matched to an outstanding request; global table invariants; atomic key and table access across threads and interrupts; target data layout and integer widths; safe start from arbitrary RAM contents; containment of single bit flips in control data; atomic persistent storage; progress and watchdog behaviour; plus two practices: a test corpus generated from the proof targets and run through both implementations, and a manifest so that every network-reading source file must have a proof.

Both reviews agree on the next code: reassembly and the authentication gate. Review 2 adds an order: first settle the open rule questions and write a thin memory and layout budget, then reassembly, then the gate with a narrow interface to the cryptography, then the real Salsa20/12 and Poly1305 behind that interface.
